# 叫停直接发给机械臂,不经过主线程

原定程序分三个线程:识别线程读帧、识别;主线程管状态逻辑、预览窗口和键盘;执行线程逐段调机械臂接口的运动。叫停(停止手势或空格)时,由主线程调机械臂接口的「停止」。

但主线程会卡住:
- 第一轮摄像头原型里,拖动预览窗口的标题栏,同一线程停住 6.8 秒;
- 站着自由活动加叫停原型里,录制循环在显示和等按键上卡了 6 次(0.3–1.4 秒),没有拖窗口,原因不明。

主线程一卡,空格读不到,认出的停止手势也要等它恢复才会去叫停。叫停原型又证实,从别的线程调 RoboDK 的 `Stop()` 很快(仿真里 3–28 ms)。

因此,谁先发现要停,谁就直接叫停:
- **空格:**单独一个按键线程,每 10 ms 用 Windows 自带的接口查一次空格键,不装包。预览窗口卡住、不在前台,都能叫停。回车、R、q / Esc 仍然只在预览窗口里认。
- **停止手势:**识别线程认满连续 3 帧,直接叫停。
- **顺序:**叫停先立一个「已叫停」标记,再调机械臂接口的「停止」。执行线程每段开始前看这个标记,已叫停就不再发下一段。主线程随后只负责切状态(倒计时、已停止)和刷新画面。
- **验收:**拖住预览窗口不放时按空格,机械臂照样在 0.5 秒内停住。

## Considered Options

- **维持由主线程叫停,另外防止预览窗口卡住(全屏置顶、不许拖动):**站着录像时那 6 次卡顿并没有拖窗口,原因不明,防不住。
- **叫停直接发给机械臂(采用)。**

(2026-09-20 第一次上 JAKA 之后:谁来叫停这一条不变;但**运动中不能读机械臂的位置**——调 `robot.Joints()` 让 RoboDK 5.9.0 崩了进程,运动中也读不到位置曲线,所以执行线程只轮询 `Busy()`,预览窗口不在运动中读位置。真机上的 `Stop()` 这次没测到;用户 2026-09-20 定「叫停暂时不测」,所以「0.5 秒内停住」目前只在仿真里验,真机的叫停用时和滑行距离等上实机时再测。)

## Consequences

- **空格变成全局的:**预览窗口不在前台时,在别的程序里按空格也会叫停。按「宁可误停,不能漏停」,用户接受。原来「按键不用全局热键」这一条,空格不再适用;仍然不为此装第三方包。
- **「停止」会被几个线程调,也可能重复调。**机械臂接口的「停止」要能从任何线程调,重复调也没有副作用。
- **状态逻辑要接住别的线程发来的「已叫停」:**执行中叫停进入回待命,回待命途中叫停进入已停止,规则不变。「已叫停」标记什么时候清、新的一段运动怎么开始,在 spec 里写明。
- **识别线程要能直接拿到机械臂接口。**写视觉部分时照这个接。
- **只在 Windows 上成立。**按键线程用的是 Windows 的接口;项目本来就只在 Windows 上跑。
- **叫停最坏多等约 0.15 秒:**RoboDK 的非阻塞 `MoveL` 本身要 63–146 ms 才返回,这期间占着连接的锁(读源码得出)。仍在 0.5 秒内;RoboDK 那一侧的自动测试里补测「正在发运动指令的那一刻叫停」。
